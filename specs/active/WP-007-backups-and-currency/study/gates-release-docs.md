### Proposed minimal post-upgrade gate (no local k3d)

Ordering principle: everything that can fail without touching production runs before the deploy; the deploy and the few runtime checks run after, and only the deploy step is the user's go-ahead (release skill already requires it).

Before deploy (automatic, run by the agent on the working tree after the 3pp update):

1. `npm ci` (lockfile resolves; `inference`: this is what the 3pp skill's last step leaves fresh anyway) then `npm test` (server plus web; about 1 minute).
2. `npm run lint` and `npm run format:check` (the release skill's step 3 already requires them; a major bump of eslint/prettier/typescript fails here, not in the cluster).
3. `npm run build` (tsc on both workspaces; catches type breaks from TypeScript, `@types/*`, better-sqlite3, vite).
4. `helm lint deploy/helm/pachanguero -f deploy/helm/pachanguero/values.secrets.yaml.example` and `helm template pachanguero deploy/helm/pachanguero -f deploy/helm/pachanguero/values.secrets.yaml.example > /dev/null` (release skill runs lint only; the template catches pins in templates).
5. `./build.sh` (image only, nothing pushed; proves `npm ci --ignore-scripts` and the better-sqlite3 prebuilt binary resolve on the new `node:<tag>-slim`). Optional and cheap, `inference`: `docker run --rm -e JWT_SECRET=<32+ throwaway chars> -e PACHANGUERO_DB=/tmp/p.db -p 8787:8787 pachanguero:<version>` then `curl -fsS http://localhost:8787/` and `curl -s -o /dev/null -w '%{http_code}' -X POST localhost:8787/api/auth/login -H 'content-type: application/json' -d '{}'` expecting 400/401 (not 500). This proves the native module loads on the new Node major, which `npm test` (dev-machine Node) does not. It needs no cluster and no k3d.
6. `npm run test:e2e` only when Playwright, vite, express, or the web framework majors moved (they exercise the dev servers, not the image); otherwise skip and say so. Browsers must already be installed; a Playwright bump may need `npx playwright install`, which needs the user's explicit permission.
7. `npm run test:sandbox`: only if the bank feed code or its HTTP/crypto deps changed and the standing session exists; it skips otherwise.

Needs the user:
- The go-ahead for `./build.sh --push` and for `deploy/deploy.sh --tag <version>` (release skill steps 5 and 7); the new version is an ordinary release, see Q-11.

After deploy (automatic, read-only, via the deployment-management skill's commands):

8. `deploy/deploy.sh` exits 0 (its `--wait` is the rollout check).
9. `kubectl --context erebor -n pachanguero get pods` shows Running, containers ready (one container after the sidecar is dropped, `inference`), restarts 0 after about 30 s; `kubectl ... logs deploy/pachanguero -c pachanguero --tail=100` shows the listen line, no migration error and no stack trace.

11. A backup file appeared under the staging directory with the new pattern, when the release changed the schema or when the new chart's periodic job has run (replaces the release skill's `ls /backups`; the exact command depends on how the hostPath is mounted: `unknown` until designed).

Needs the user (after deploy):
- `curl -I https://pachanguero.duckdns.org` answers 200 over a valid certificate (outside the house, Caddy toggle; the release skill already marks it unverified until confirmed) and, ideally, a real login in a browser once (no automatic credentials exist in the repo or should be used; accounts are the organiser's). ## Q-11

### How the release machinery works today

- `ai-kit/skills/pachanguero-release/SKILL.md`. Steps: 1 clean tree (stop if not); 2 choose version from `git log vX.Y.Z..` (patch = fixes and docs; minor = new behaviour or a new `MigrationStep`; major = data or manual operator step breaks; if equal to current version skip only the bump; if the tag exists stop); 3 `npm test`, `npm run lint`, `npm run format:check` (+ sandbox and guided checklist if the bank feed is touched); 4 `scripts/bump-version.sh X.Y.Z`, `helm lint`, `./build.sh`, then commit `package.json`, `package-lock.json`, `deploy/helm/pachanguero/Chart.yaml` as `Release X.Y.Z` (no co-author trailer, never `--no-verify`); 5 ask, then `./build.sh --push`; 6 `git tag -a vX.Y.Z`; 7 ask, then `deploy/deploy.sh --tag X.Y.Z`; 8 verify with "Success" and "Checks" of `docs/deployment.md` plus the `-before-migration.db` listing after a schema change; 9 report; the user pushes the commit and tag (agent never pushes). Rules: stop for the user's go-ahead before push and deploy; a pushed or deployed version is never reused (no re-push, no moved tag; fix forward with the next patch).
- `scripts/bump-version.sh`: `npm version --no-git-tag-version`, `sed` of the chart's `version` and `appVersion`, then `--check` (three places agree); refuses when tag `vX.Y.Z` exists. Edits files only.
- `build.sh`: version read from `package.json`; `DOCKER_BUILDKIT=1 docker build -t pachanguero:<v>` (no `--pull`, no build args), tags `:latest` and `192.168.1.87:30500/pachanguero:<v>` and `:latest`; `--push` pushes both registry tags.
- `deploy/deploy.sh`: `helm upgrade --install pachanguero ... --kube-context erebor --namespace pachanguero -f values.secrets.yaml --set image.tag=<tag> --wait`; `--restart` adds `rollout restart` and is for development only. The chart pulls from `registry.local:5000` (k3s maps it to the NodePort registry) with `imagePullPolicy: Always`, strategy `Recreate`, replicas 1.
- `docs/deployment.md#releasing`: bump and commit, `./build.sh --push`, `deploy/deploy.sh --tag <version>`; Success (3 conditions); rollback (previous `--tag`, restoring the `-before-migration.db` first if the release migrated).

### The Dockerfile and picking up new OS packages

`Dockerfile`: `FROM node:26-slim AS build` and `FROM node:26-slim` (both floating on the tag `node:26-slim`); no `apt-get` anywhere; no `ARG` of any kind (no date, no refresh arg); `build.sh` passes no `--build-arg` and no `--pull`. Consequence (`inference`, from how Docker caches): a rebuild on a machine that already has `node:26-slim` locally reuses that stale base and picks up no new OS packages; even with `--pull` the OS only moves when the Node project republishes the tag. A rebuild from a clean Docker cache picks up whatever the tag points to that day. There is no layer that upgrades OS packages, so today only a new `node` image publication (plus a local pull) refreshes them. `docs/deployment.md` "Node version or a native dependency" row says to change "both `FROM` lines".

t4m: `k8s/charts/backup-shipper/image/Dockerfile` has `ARG BASE_IMAGE`, `FROM ${BASE_IMAGE}`, `ARG OS_REFRESH` immediately before `RUN apt-get update && apt-get upgrade -y --no-install-recommends && apt-get install ...`; `k8s/management/build-shipper-image.sh` runs `docker build --pull --build-arg BASE_IMAGE=... --build-arg OS_REFRESH=$(date -u +%F)`. The date changes the layer's cache key daily, so a build re-runs the upgrade on a new day and reuses it within one. The monolith Dockerfiles do the same (`trading-monolith/docs/build-system.md` "Base images, one OS, and the OS upgrade layer": `build-pins.env` pins full image references; `build-images.sh` uses `--pull` and passes pins as build args declared before the first `FROM` with no default). The base is Debian-based and pinned by exact tag. In pachanguero the base `node:26-slim` is Debian-based (`inference`: the `-slim` variants are Debian), so `apt-get upgrade` is available, but the final runtime stage runs as `node` after `USER node` and the apt layer would have to precede that, in the runtime stage.
Needed in pachanguero (design input for the WP): an `ARG OS_REFRESH` plus an `apt-get update && apt-get upgrade -y` layer in the runtime stage (the build stage is discarded; only the final stage's OS ships), `build.sh` adding `--pull` and `--build-arg OS_REFRESH=$(date -u +%F)`, and the pin made an exact tag (see Q-07/Q-09; the Dockerfile row of "Deployment impact of a change" and the "Node version" row both name the `FROM` lines).

### How the t4m skills hand a 3pp update over

- `t4m-3pp-update` "All": report, `update all`, show `REFUSED`/`skipped` lines, if `backup-shipper/values.yaml` changed raise its `image.tag`, run Checks once, on failure ask (restore all vs fix), remove unused images, show changed files, ask to commit (stop unless yes), commit in each repo that changed, then `skill: t4m-release`. It "Never releases; hands over to t4m-release." Description says so.
- `t4m-release` has no special rule for an upgrade-only change; the version comes out of the machinery: `release-changed-services.sh --explain` lists a service when its own directory changed, a bundled package changed, or "the shared environment changed (uv.lock, build-pins.env, a pinned container image or tag in the chart values): every service"; "Every other listed service gets a patch" in `release-apply-bumps.sh`; the skill's SemVer rule: "breaking interface change is major, additive is minor, anything else is patch". So a 3pp update is a patch for every service (`inference`: unless a service's interface moved, which step 2 judges by reading the diff). A shipper-only change "lists no service. Release anyway", and raises `image.tag` first when its Dockerfile or `image.base` changed. `docs/deployment/release.md` "Release record and tags": the release id is "the previous id raised by the highest bump any service took, patch when only a chart changed"; "A release that changes only the shipper is a patch release". `docs/deployment/third-party-currency.md`: "OS security patches arrive by an OS package refresh: rebuild the five images, then release. The shipper takes a refresh only with a new `image.tag`."
- Not found (searched `t4m-release`, `release.md`, `third-party-currency.md`): an explicit sentence for a pure OS-refresh rebuild where no file changes (nothing to list); `unknown` how t4m versions that case in the monolith services (`inference`: a manual `bump_versions.py --part patch`).

Pachanguero equivalent rule to adopt (proposal): any upgrade-only release is a patch (`pachanguero-release` step 2 already says "Patch: fixes and docs"; add upgrade-only changes and OS refresh to that line), unless an upgraded dependency changed existing data or an operator step (major) or a `MigrationStep` is included (minor). A rebuilt-on-current-OS image with unchanged code still needs a new version, because "a version already pushed or deployed is never reused" and `imagePullPolicy: Always` with `--restart` is development-only.

### Backup before release: today vs t4m

Pachanguero today: no release backup exists. The only automatic one is the app's own before-migration backup: `SchemaMigrator` (opened by the new pod at start-up) calls `DatabaseBackup.create('before-migration')`, only when an older schema version is found, writing `pachanguero-<timestamp>-before-migration.db` into `PACHANGUERO_BACKUPS` (`/backups` PVC) with `VACUUM INTO` of a `.part` file renamed when done (mode 0600, dir 0700, never deletes; `server/src/db/database-backup.ts`, `AGENTS.md` "server/src/db/"); if it cannot be written the server does not migrate or start (`docs/backup_and_restore.md` "Two kinds of backup"). Consequences for this WP: (a) it happens after the new image is already deployed, not before; (b) it does not happen for an upgrade-only release (no schema change), so such a release has no pre-release backup at all today, though the daily sidecar backup is at most 24 h old; (c) its name starts `pachanguero-<local timestamp>`, uses a `.part` suffix rather than a `.` prefix and carries no version, so it does not match the shipper's `NAME_RE` (`<kind>_<UTC timestamp>_<version>.<ext>`, `.` names ignored; `trade4me-server/docs/deployment/backup-contract.md` "Where and how to write it") nor does `calendar.timestampOf` produce UTC (`inference`: it is a `LocalCalendar`; confirm in Q-05). Rollback today: restore the `-before-migration.db` of the failed version, then redeploy the previous tag (`docs/deployment.md#releasing`).

t4m: `release.sh` takes a release backup before it builds, pushes or deploys: step 3 of its order of steps, `k8s/management/backup-now.sh --kind release --release "$RELEASE_ID"` (skipped only with `--skip-backup`), then starts a shipper job `kubectl -n backup create job --from=cronjob/backup-shipper backup-shipper-release-<utc>` (not awaited; failure to start only warns), and `check-database-image.sh` restores that backup into a scratch namespace to try a new database image. The backup is named `release_<UTC>_<release>.tar` (`recovery.md` "Backups").

Gap for pachanguero (design input): to name the file `release_<UTC>_<version>.db` and have it exist before the deploy, something must take it before `deploy.sh` moves the pod: either `pachanguero-admin backup --kind release --version X` run via `kubectl exec` in the old pod (the old pod is Running until `Recreate` stops it; it is the pre-deploy state), added to `deploy/deploy.sh` or the release skill as a step before `deploy.sh`; or, as the vision implies ("the before-migration one as `release`"), have the app write the before-migration file in the new pattern with the new version (the version the new pod is about to run; but it then only exists for schema changes). `unknown`: which the author chooses; the vision text maps before-migration to `release`, which leaves upgrade-only releases without one. Recommend, as `inference`, a pre-deploy release backup for every release (cheap, one `exec`), so the upgrade-only case is covered.

### Order of operations for an upgrade-only release in pachanguero (proposal)

1. Start clean: `git status` empty (release skill step 1). The 3pp skill leaves its changes uncommitted until asked.
2. `pachanguero-3pp-update`: report, update all (LTS preferred else latest; exact tags), light gate steps 1 to 7 of Q-10 (before deploy), remove unused images, show changed files, ask to commit, commit (message of the 3pp work; not `Release X.Y.Z`), then hand over to `pachanguero-release` (t4m pattern, "Never releases").
3. `pachanguero-release`: choose version = patch (upgrade-only; say why), step 3 verify (already passed by the gate but the skill's step is cheap; do not duplicate it, `inference`: the release skill can say "the 3pp gate counts if nothing changed since"), step 4 bump/helm lint/`./build.sh` (new, with `--pull` and `OS_REFRESH`, see above), commit `Release X.Y.Z`.
4. Ask. Take the release backup from the running (old) pod to the staging directory (new step; backup name `release_<UTC>_<old running version?>`: `unknown` whether the release backup carries the version being deployed or the one it protects; the contract says "named with that version", i.e. the version being deployed: `backup-contract.md` Name row `release` "taken before deploying a version, named with that version"). Then, optionally, trigger a shipper job as t4m does (not awaited; `unknown` with papiros possibly off).
5. `./build.sh --push`; tag `vX.Y.Z`; ask; `deploy/deploy.sh --tag X.Y.Z`.
6. Post-deploy checks 8 to 12 of Q-10; the user confirms the public `curl`. Report; the user pushes commit and tag.
7. If the deploy fails: roll back to the previous tag (`docs/deployment.md#releasing`); no schema restore for an upgrade-only release. A pushed version is never reused: fix forward with the next patch.

Signal: surprising (there is no release backup at all today, and the before-migration backup happens after the new image deploys and never for an upgrade-only release; the Dockerfile has no OS refresh and `build.sh` has no `--pull`, so a rebuild does not necessarily bring new OS packages)
